# S5 execution findings

Things noticed while porting that are out of scope for the round that found them. This file is the only place such findings are recorded — never a background-task chip. Each entry says what is wrong, where, and who should fix it.

## Closed

**The four retired `migration status` flag redirects are declared.** The engine accepts a flag redirect only when `from` names a mounted command, so they waited for `migration status` to be ported. All four (`--graph`, `--all`, `--limit`, `--ref`) now sit on `ormCommandFamily` with `{bin}` replacements, and `test/orm/cli.test.ts` asserts both the declared list and that an old invocation settles as `CLI.COMMAND_MOVED` naming the replacement. Two construction rules the declaration had to satisfy, both worth remembering: the flag name is camelCase (it transliterates to `--kebab-case`), and the command must not still accept the flag — including the engine's own shared flags, which every command answers whether or not it declared them.

**Vacuous assertions in `migration list`'s first test file.** `test/orm/migration-list.test.ts` seeded a migration package with `operationClass: 'schema'`, which the operation schema rejects, so the loader silently dropped the package and several assertions ran against an empty project — including one that expected the empty-project line immediately after seeding. Found while writing PR 2's tests; fixed in PR 1 (`014bb604cb`) by seeding a valid `additive` operation, asserting the rendered table, and covering the empty project as its own case. Worth remembering as a class: a seeded fixture that fails validation makes a test pass for the wrong reason, and the engine harness surfaces no warning when it happens.

**`normalizeError` flattened the repo's other error shape.** It required a `toEnvelope` method, which values from `structuredError()` do not have, so each one became `CLI.UNEXPECTED` and lost its code, `why`, `fix`, `where` and `meta`. The control-API client alone raises six. Found by the principal-engineer review of PR #29970 (finding F03); fixed in the review round (`7080919a57`) by narrowing through the repo's own `isStructuredError`, which recognizes both shapes and validates the dotted code. The same change closed CodeRabbit's finding on the predicate promising `${string}.${string}` while checking only for a string: a non-conforming code now maps to `CLI.UNEXPECTED` with the rejected value kept in `meta.code`.

**A thrown error settled as a malformed envelope, and the fix had to be structural.** The engine's `settleThrown` guard is a duck test on `name` + `code` + `toEnvelope`, and prisma/prisma's `CliStructuredError` carries all three — so a thrown error was *accepted* and settled by calling our `toEnvelope()`, which writes the non-protocol `fix` and leaves `nextActions` undefined. Fixed in `7080919a57` by making the boundary the definition rather than the handler: `defineOrmCommand` wraps `defineCommand` with a top-of-handler catch running `normalizeError`, and every ORM command is defined through it, so a new command inherits the boundary by construction. Worth remembering as a class: when two packages export a class of the same name, a structural guard on the *name* silently accepts the wrong one, and the failure shows up as a shape defect rather than a type error.

**Eleven `finally { await client.close() }` sites could discard the result they were cleaning up after.** A rejection out of a `finally` supersedes the value the `try`/`catch` returned, and the close is most likely to reject exactly when `connect()` failed and there is nothing to close — so the mapped connection error was the one thrown away. Raised by CodeRabbit against `orm/migration/log.ts` on PR #29973; fixed in `b45096dd5d` with one named `closeQuietly` helper used at all eleven sites, ORM and commander alike.

## Open

**`init`'s three bespoke exit codes settle as completed-with-findings, and exit 4 is the weakest of the three under ADR 239's test.** §4 rules 4/5/6 into the command's `exitCodes` map, and the port builds that. The justification differs per code. A failed contract emit (5) and a failed agent-skill install (6) leave a project that exists and works — `init` did its job and is reporting what happened next — so "was finding these problems the job?" reads yes without strain. A failed dependency install (4) does not: the scaffold is on disk but the project cannot run, and read literally, ADR 239 would send it to the errored path at exit 2. It stays at 4 for two reasons. The run has a result a caller needs — `filesWritten`, `packagesInstalled.skipped`, and the next actions to resume — where an errored settlement carries no result at all; and exit 2 would collapse "your project is scaffolded but not installed" into the same number as "you invoked me wrong and nothing was written", which is the distinction the exit-code table exists to draw. Owner: an operator who wants the literal reading; the change is one `notOk` and one divergence row.

**`CLI.INIT_REINIT_NEEDS_FORCE` and `CLI.INIT_USER_ABORTED` have no raise site left in the ported command.** R-S5-13 keeps both spellings and rewrites the first one's prose for consent, which reads as though the port still raises it. It cannot: `prompt.consent` with a token throws the engine's `CLI.CONSENT_REQUIRED` before a handler sees anything when the session cannot ask, and a token consent resolves to `true` or throws — there is no `false` for the handler to convert into `CLI.INIT_USER_ABORTED`. Both codes survive because the commander shell still raises them, and both error-reference entries now say which shell raises what. Owner: nobody, unless the cutover wants them deleted with the commander.

**The package-manager capability gives a handler no way to learn which manager it drove.** `install` and `run` resolve `Result<void, …>` — success carries nothing back, and `resolvePackageManager` is engine-internal. `init` needs the name twice: the quick reference and README it writes into the user's project print example commands (`pnpm prisma-next contract emit`), and the pnpm-to-npm fallback needs to know the failed attempt was pnpm's. The second is served by the failure's `meta.manager`; the first is not served at all, so `init` resolves the manager a second time itself, mirroring the engine's order (the project at cwd, then `npm_config_user_agent`, then the default) over `ctx.cwd` and `ctx.env`. Two consequences worth naming: the two resolutions can disagree if the engine ever changes its order, and a host that sets `Runtime.packageManager` moves the engine's answer without moving the handler's. The fix is small — return the resolved manager on success, or expose it on `ctx.packages`. Owner: prisma-cli.

**§6 predicted `CLI.INSTALL_FAILED` and `Result<{command}, …>`; the shipped capability is `CLI.PACKAGE_MANAGER_FAILED` and `Result<void, …>`.** Everything `init` needs is on the failure's `meta` (`form`, `manager`, `command`, `exitCode`, `stderrTail`) and its `nextActions` carry the redacted command line, so nothing was blocked. The contract's §6 text should be corrected to the shipped surface so the next reader does not go looking for a code that does not exist. Owner: the contract.

**The engine's redaction is compatible with a caller-side error predicate, deliberately.** `redactSecrets` strips URL userinfo and secret-named values but leaves everything else verbatim, and its comment says so — which is what makes `init`'s pnpm-fallback predicate work against `meta.stderrTail`. Worth recording because the predicate would silently stop matching if that ever changed, and no test outside `init` would notice.

**`--keep-previous-facade` is a new flag with no predecessor.** The Style Guide requires a flag for every prompt. `init`'s sixth prompt — drop the previous target's package when re-scaffolding across targets — had none: `--force` answered it, and `--force` does not port. The prompt's default is "remove", which `-y` and a non-interactive run take, so the new flag exists to express the other answer. Owner: nobody, unless the operator wants a different spelling.

**`init` writes package-manager command lines into the user's project, and R13 permits it.** §6 says a handler "never spells a package-manager command". The scaffolded `prisma-next.md` and `README.md` contain example invocations (`pnpm prisma-next contract emit`) — documentation content, byte-identical to what the commander wrote, and nothing the CLI executes. Recorded so the distinction between running a manager and documenting one is written down rather than rediscovered.

**Two `--json` shape changes `init` makes, both consequences of rules rather than choices.** The `nextSteps` strings lose their package-manager prefix (`prisma-next contract emit`, not `pnpm prisma-next contract emit`), because the handler may not spell one. And on a 4/5/6 run the document is present at all — the commander wrote an error envelope there — with `ok: true`, which now means "the scaffold was written" while the envelope's `exitCode` and `diagnostics` carry the failure. Owner: the divergence file, which lists both.

**Two modules had to be split so the ported `init` does not drag clack and `node:child_process` into the command tree.** `src/commands/init/inputs.ts` mixes pure flag validation with clack prompts, and `skill-install.ts` mixes the skill source list with an `execFile` runner. Importing either from `src/orm/` put them in every `test/orm/*` file's module graph, and under `isolate: false` that defeated `test/commands/init/init.test.ts`'s file-scope mocks of both modules — 75 of its tests went red, and one of them spawned a real network install. The pure halves now live in `input-values.ts` and `skill-sources.ts`, which both shells import. Worth remembering as a class: a module-scope mock is defeated by any other file that loads the mocked module's *consumer* first, so a port should import the narrowest module it can rather than the one that happens to export the symbol.

**The engine renders a command's documented exit codes nowhere.** `init --help` lists every flag but not the 4/5/6 table its `exitCodes` map declares, where the commander printed it in the command description. The numbers are in the contract and in the error reference, but not where a user reading `--help` would find them. Owner: prisma-cli, if a help section for documented exit codes is wanted.

**Measured behaviour of the recorded live-prompt defect on engine 0.0.9, which narrows it.** Driving the built binary through a real pty: `prompt.select` and `prompt.confirm` answer correctly to Enter and a full interactive `init` completes and writes the scaffold; `prompt.consent` with a token accepts the token *typed* and grants (and refuses a bare Enter, so the placeholder is not being submitted on the user's behalf); `prompt.text` echoes nothing when characters are typed and the run does not settle. Both consent and text go through the same `clack.text` call with the same stream adapters, differing only in `placeholder` versus `defaultValue`, so the fault is narrower than "every prompt". Owner: unchanged — prisma-cli's `clack-renderer.ts` / `prompts.ts`; recorded here as evidence for whoever picks it up.

**Engine 0.0.9 makes `Runtime.isCI` required and drops `'unknown'` from `Runtime.packageManager`.** Both are compile errors in `src/orm/cli.ts` at 0.0.8's spelling, and both were fixed here: `isCI` wires the repo's existing `ci-info` helper, and the bin now supplies no `packageManager` at all — a host's answer overrides the engine's detection outright, and this bin knew nothing the engine's own walk from cwd does not. 0.0.9 also adds `LoadedConfig.path`, which is the field two earlier findings are waiting on.

**ENGINE DEFECT — the live interactive prompt never accepts a typed value (engine 0.0.8).** Reaches every prompting command in every consumer, not just the ORM port; the platform CLI's consent commands have the same shape. Symptom: under a real pty the prompt renders, but typed characters never compose into a value — Enter re-validates an empty answer and the run never settles. Isolation already done by the `db update` port: plain `clack.text` works under the same pty harness, and still works when handed exactly the engine's own adapters (`toReadable`'s `Readable.from(stdin, { objectMode: false })` input wrapper and `toWritable`'s `new Writable({ write })` output wrapper) — so the fault is in the engine's live prompt path rather than in either adapter alone or in any handler. `clackCapable` must have returned true (the clack prompt rendered), so `runtime.stdin.setRawMode` is defined and raw mode was requested. Non-interactive paths are unaffected, and the test harness's line reader covers grant/decline/cancel, which is why no test catches it. Next step for whoever picks this up: check whether keypresses reach clack at all through the `Readable.from` wrapper, and whether raw mode is actually in force on the underlying fd rather than merely forwarded. Owner: prisma-cli (`packages/cli-engine/src/execution/clack-renderer.ts`, `prompts.ts`).

**The engine's own consent errors already reach exit 3, so R-S5-14's interim was never needed for `db update`.** The contract says a declined consent settles at the handler's own code and exit 2 until §8 item 4 exports the cancellation constructor. It does not have to: `prompt.consent` never returns `false` — it returns `true` or throws — and the errors it throws are the engine's own `CliStructuredError` values (`CLI.PROMPT_CANCELLED` on Ctrl-C or a closed stdin, `CLI.PROMPT_INVALID` on a mistyped token where re-prompting is impossible, `CLI.CONSENT_REQUIRED` where there is nobody to ask). `normalizeError` returns an engine-built error unchanged, so `notOk(...)` carries the code through to `settleErrored`, which maps `CLI.PROMPT_CANCELLED` to 3 and everything else to 2. The handler's job is only to not restate the error as its own: `db update`'s catch re-throws anything that is `instanceof` the engine's class before its `CLI.UNEXPECTED` fallback. No `db update` decline code was minted, and §8 item 4 is not a blocker for this command. Owner: the divergence file, which should say the decline exits 3 today rather than "2 interim".

**The engine treats `--yes` as a non-interactive session for consent, and `--confirm` grants even alongside it.** `consent()` branches on `state.yes || !state.interactive` as one condition, so `-y` on a real terminal does not prompt — it goes straight to the `--confirm` check and fails with `CLI.CONSENT_REQUIRED` ("`--yes` cannot grant"). The mirror image is that `--yes --confirm <token>` succeeds. Both are the engine's rulings, not the handler's; the port pins them in `test/orm/db-update-consent.test.ts` because the second one surprises anybody who reads `--yes` as "never destroys".

**A non-interactive refusal no longer names what would have been destroyed.** The commander settled `MIGRATION.DESTRUCTIVE_CHANGES` with `meta.destructiveOperations`, so a CI run could read the list out of the error envelope. The port asks for consent instead, and the refusal is the engine's `CLI.CONSENT_REQUIRED`, whose meta carries the consent token alone — a handler cannot enrich an error the engine mints inside `prompt.consent`. The operations are still in the question text on stderr (§4 pins them there), and a granted run still lists them in its result document. Owner: an engine change that lets a command attach meta to a consent refusal, if the operator wants the machine channel to keep the list.

**The consent prompt does not work through the real binary on a real terminal — an engine 0.0.8 rendering defect.** Driving `dist/bin.mjs db update` under a pty (`expect`), the destructive plan is computed, the clack prompt renders, and every keystroke re-renders it — but the typed token never composes into a value, so Enter re-validates an empty answer and the run never settles (it had to be killed). The same pty harness drives plain `clack.text` to a correct answer, and so does `clack.text` given exactly the engine's own adapters (`Readable.from(process.stdin[Symbol.asyncIterator]())` marked `isTTY` for input, `new Writable({write})` for output), which rules out both adapters in isolation and points at the engine's live-invocation prompt path. Every non-interactive answer is unaffected and was verified through the same binary: no consent → 2, `--yes` → 2, wrong `--confirm` → 2, `--confirm <database>` → 0 with the column actually dropped. The engine harness's scripted-answer path (which `createTestCli` uses, and which is the line reader rather than clack) grants, declines and cancels correctly, so the command's own logic is covered. Owner: prisma-cli, and this blocks nothing that a `--confirm` cannot answer — but it means no user can grant consent by typing today.

**The demo's consent token is `template1`, which is a Prisma dev-server artifact rather than a name a user would recognise.** `@prisma/dev` hands out `postgres://…/template1`, so STOP-5's rule ("the database name parsed from the resolved connection URL") makes the token `template1` for every dev-database run — the demo, and every journey. It is correct by the rule and still worth knowing before anybody writes docs promising "type your database name". The fallback to the target id has since been narrowed to the last of four steps (see the STOP-5 entry below): a URL with no path now yields its host and a driver connection object yields the `database` it names, and only a shape none of the rules recognise — a libpq `key=value` string, a bare file path — still falls back. Owner: nobody, unless the operator wants a token that reads better for dev databases.

**Planner warnings had nowhere to go on a failed apply.** `MigrationCommandResult.warnings` is set only by `db update`, and `db init`'s port left it unrendered for that reason. The completed path now renders a `warn` summary plus a `list` in the shared `orm/db/migration-blocks` module. The failed path cannot: `notOk(error)` takes no diagnostics, and the engine renders no `meta` for an errored settlement, where the commander's error formatter printed `meta.plannerWarnings`. The port reports them as `warn` message events before returning the failure, which reaches human stderr and json frames alike — but `--quiet` (log level `error`) drops them, where the commander printed them regardless. Owner: nobody; revisit if the engine ever lets a handler attach diagnostics to an errored settlement.

**`db update` reached this branch before `db init` and `migrate` merged, so the branch is stacked.** The command is `db init` plus consent and shares `orm/db/prepare.ts`, `orm/db/migration-blocks.ts` and `orm/progress.ts` with it, none of which exist at the ORM-port tip — they are on `s5-orm-db-read`. `s5-orm-db-update` therefore opens with a merge of that branch rather than re-writing those modules, which keeps one copy of the scaffold and makes the eventual integration a fast-forward. Owner: whoever sequences the merges — `s5-orm-db-read` has to land first.

**The contract's "`migration check` unexpected-throw moves 2 → 1" divergence is wrong, and the ADR's exit-1 band is unreachable from an ORM command.** §7 and R-S5-12 both say deleting `migration check`'s catch-all wrapper moves an unexpected throw from exit 2 to the engine's exit 1. It does not, and cannot: `defineOrmCommand` (R-S5-31, landed in PR 1) wraps every handler in a top-of-handler catch that runs `normalizeError` and returns `notOk(...)`, and the engine's `settleErrored` maps every code except `CLI.PROMPT_CANCELLED` to exit 2 (`execution/settlement.ts`). So a genuine programming error in any ORM command settles as `CLI.UNEXPECTED` at exit 2, exactly as it did under commander — what actually changed is the shape (a structured envelope with typed next actions instead of a result document whose `failures` list is empty). The two rules are in direct tension: R-S5-31 wants one conversion at the boundary, and R-S5-12 wants an uncaught throw to reach the engine. Resolving it fully means narrowing `defineOrmCommand`'s catch to errors that pass the repo's own `isStructuredError` and re-throwing everything else, which changes every ported command's failure behaviour and still needs a ruling. **Interim, landed here:** `defineOrmCommand` re-throws an `InternalError` and converts everything else, so the one class the ADR reserves exit 1 for reaches the engine and settles there as `CLI.INTERNAL_ERROR`. That class is not hypothetical in this round — `combine-verify-results.ts` throws one on an empty per-space map, reached from both `db verify` branches, and `db sign` now throws one when a family returns a sign result that did not sign. Both `db verify` and `db sign` re-throw it from their own local catch too, so the conversion in `verificationThrow` cannot swallow it on the way out. Nothing else changes: a `TypeError` still settles as `CLI.UNEXPECTED` at exit 2. Owner: an operator ruling on the full narrowing; until then a genuine bug is distinguishable from a bad connection string, and the divergence entry claiming "unexpected throw moves 2 → 1" should still be struck, because the unexpected throw does not move.

**`db verify`'s `MIGRATION.CONTRACT_SPACE_VIOLATION` is a drift finding wearing a precondition's code, and `--marker-only` is where that stops being tolerable.** `operations/db-verify.ts` raises that one code from two places: an introspection failure (the verifier could not run — exit 2 is right) and `mapMarkerCheckFailures`, which reports a marker hash mismatch, missing marker invariants, or an orphan marker row in a contract space (drift — arguably exit 4). §4's list of codes that become findings does not include it, and nothing on the value distinguishes the two producers except the presence of `meta.violations`, so the port keeps both at exit 2 rather than sniffing meta. The consequence to know before shipping: `db verify --marker-only` against a database whose extension-space marker has drifted exits 2 — "could not do the job" — in the one mode whose entire job is the marker check. The single-contract marker check that runs first does settle its findings at 4, so which number a marker finding gets depends on which space the marker belongs to. Owner: whoever wants per-space marker drift to settle like app-space marker drift; the fix is two codes at the raise site, not a shape test at the handler.

**Engine-derived docs links do not point at the anchor the docs page uses.** A diagnostic the engine decorates gets `docsBaseUrl + code`, so `db verify`'s drift finding links to `…/error-reference/CONTRACT.SCHEMA_VERIFICATION_FAILED`, while the repo's own `docsUrlFor` produces `…/error-reference#CONTRACT.SCHEMA_VERIFICATION_FAILED` — the form the page actually anchors. Every engine-decorated diagnostic in the family has the wrong shape; errors that carry their own `docsUrl` are unaffected. Introduced with the family's `docsBaseUrl` in PR 1 and only visible once a command emitted diagnostics. Owner: the family declaration — `docsBaseUrl` needs to end in `#`, if the engine's concatenation allows it, or the engine needs to let a family phrase the link.

**"Declare exactly the config sections a command reads" has no surface left to declare.** STOP-12 nests the whole ORM configuration under one `orm` section, and `needs.config` takes a section token, not a subsection list. The commander commands named their subsections in `loadConfigForSections(...)` — `db verify` and `db sign` read `family`, `target`, `adapter`, `driver`, `extensions`, `db`, `migrations`, `contract`; `migration check` reads all but `driver` and `db`. Under the port all three simply declare `needs: { config: ormConfigSection }` and the distinction is gone, which is the divergence STOP-12 already records. Owner: nobody; noted so the next port does not go looking for a granularity that no longer exists.

**A schema diff issue carries no dotted code of its own, so drift is one diagnostic per contract space rather than one per element.** §4 lists "the per-space schema findings" among the codes `db verify` reports, which reads two ways. The port takes the per-space reading: one `error` diagnostic per contract space whose `VerifyDatabaseSchemaResult.ok` is false, carrying that result's `code` and its element paths in `meta.issues`, plus the synthesized `CONTRACT.MARKER_REQUIRED` in the one case where only the unclaimed list fails a strict verdict. Per-element diagnostics were rejected because a `SchemaDiffIssue` is a path plus which side is present — there is no code to put on it, and repeating the space's code on twelve rows would be noise. The elements are still individually visible: they are the children of the drawn `tree` block and the `issues` array in the `--json` document. Owner: nobody unless the operator wants per-element diagnostics, which would need codes minting.

**`db verify --strict` almost never reaches the synthesized `CONTRACT.MARKER_REQUIRED`.** `combineVerifyResults` stamps that code when the combined verdict fails and the app space's own result carried none — the "only the unclaimed list failed it" case. In practice the per-space verifier already fails the space with `CONTRACT.SCHEMA_VERIFICATION_FAILED` when strict mode rejects an extra column, so the journey that exercises strict drift (`drift-schema` N.03) reports that code, not the synthesized one. The synthesized branch is covered by a unit test that forces it. Owner: nobody; recorded because the error-reference entry for `CONTRACT.MARKER_REQUIRED` now describes a path that is real but rare.

**`CONTRACT.MARKER_REQUIRED` is the third code in this round doing two unrelated jobs.** It means "this command needs a signed database and found none" — a precondition failure at exit 2 — and it is also the code `combineVerifyResults` stamps on a strict verdict that failed only because the database holds elements no contract declares, which is a finding at exit 4. Those two have nothing to do with each other, and a consumer matching on the code alone cannot tell which it got; only the exit code separates them. This joins `MIGRATION.CONTRACT_SPACE_VIOLATION` (introspection failure vs per-space marker drift) and, in the other direction, `CONTRACT.VERIFY_FAILED` as the catch-all. The error-reference entry now says so rather than describing both meanings as if they belonged together. Owner: whoever mints the split; the fix is a second code at the `combineVerifyResults` stamp site, not at the handler.

**Warn-grade findings produce no diagnostics at all, so a `--json` consumer reads warnings from two places depending on the command.** `db verify` renders schema warnings and lenient unclaimed elements as `warn` rows in the human tree and as fields of the result document, and attaches no `Diagnostic` for them — only `error`-grade findings become diagnostics. `migration status`, ported earlier, does emit `warn` diagnostics on the envelope. So a consumer reading `envelope.diagnostics` sees `migration status`'s warnings and misses `db verify`'s, and has to reach into the result document for the latter. Both readings are defensible on their own — the ADR requires a non-zero exit for an `error` diagnostic and says nothing about warnings — but they are not the same reading, and nothing in §4 chose between them. Owner: whoever settles whether warn-grade findings ride the envelope; recorded so the asymmetry is a decision rather than an omission.

**Hazard (pre-existing, not fixed here): `loadAggregateIntegrityViolations` swallows every error and returns an empty list.** An unreadable `contract.json`, a corrupt `migrations/snapshots/` directory, or a family whose `deserializeContract` throws all produce `[]` from its `catch`, so the whole aggregate-integrity pass — disjointness, orphan space directories, contract-space target mismatches — silently does not happen and `migration check` reports "All checks passed" at exit 0. The behaviour is faithfully ported from the commander command and is not new. What is new is that exit 0 now carries weight it did not carry before: the port makes 0/4 the way this command reports its verdict, so a caller that treats 0 as "the artifacts are sound" is trusting a pass that may never have run. Owner: whoever fixes the swallow; the fix is to return the failure rather than an empty list, which makes the unreadable-contract case an errored settlement at exit 2.

**`db sign` cannot name the config file it was run against, so its result document reports a fixed spelling.** `client.sign({ configPath })` writes that string into the sign result's `meta`, and the commander passed the resolved `--config` path. `CommandContext` still carries no loaded-config path (the same gap already recorded for `contract emit`), so the ported handler passes the literal `prisma-next.config.ts`. Wrong only for a run whose `--config` names another file. Owner: whoever adds the config path to the context — this is now the second command waiting on it.

**Two journeys asserted a `db verify` exit code that the commander never actually produced.** `drift-marker` P2 (corrupt marker) and K.01 (missing marker) both expected exit 2 for what the inventory calls a marker finding, and `drift-schema` M.01 expected exit 1 for schema drift — the two exit codes §7 says converge on 4. Both now assert 4 plus the dotted code of the finding, which is the assertion that would have caught a silent code change. Same shape as the vacuous-assertion finding above: an exit-code-only assertion passes for the wrong reason whenever two failure families share a number. Owner: closed here.

**The CLI package's test suite is order-dependent, and it was so before this round.** Under `isolate: false` with one worker, `pnpm --filter @internal/cli test` passes in its default order but fails under a shuffled file order on roughly a third of seeds — measured at the round's base commit (seeds 2, 3 and 5 of 1/2/3/5/7/11/13/17 red) as well as with the three new files added. The failures are always in commander-era files that combine a module mock with a dynamic `await import` of the module under test (`migration-legend-commands`, `migration-list-json-golden`, `migration-status`), plus the already-recorded `client.test.ts` emitter-mock flake. The three files added here pass under five distinct orderings of `test/orm` and add nothing new to the pattern. Owner: the same test-infrastructure round that owns the `@internal/emitter` mock flake; the fix is the same one — reset the registry and re-acquire the mocked handles inside `beforeAll` rather than mocking at file scope.

**`lint:framework-vocabulary` cannot tell a SQL table from a terminal one.** The check forbids `table` and `column` in `packages/1-framework` because they are DDL words, but the renderer uses them for a terminal grid and for text columns, so the renderer conversion in #29978 arrived seventeen lines over the threshold with no SQL in any of them. Sixteen were reworded (`LedgerGrid`/`headings` rather than `LogTable`/`columns`; "field" and "display width" in two comments), which is the better vocabulary anyway in a codebase where those words already mean something else. The threshold went up by one for the two lines that are somebody else's names: `proc.stderr.columns` (Node's terminal width, reached through the engine's `Runtime` field) and `{ kind: 'table', columns, rows }` (the engine's `Block` shape). Owner: nobody yet — but any future renderer work in the framework layer will hit the same false positives, so if it recurs, teach the check to shield the engine's `Block` field names rather than raising the number again.

**The `prisma-next` bin still points at the commander shell.** `package.json` maps it to `dist/cli.js`, which shims `dist/cli.mjs`; the `dist/bin.mjs` built from `src/bin.ts` is never loaded by the binary. **`vscode-jsonrpc` mis-reads a chunk that is a plain `Uint8Array` rather than a Node `Buffer`.** The engine types `InputStream` as `AsyncIterable<Uint8Array>` and `createTestCli` yields exactly that (`inputStreamFromString` returns `new TextEncoder().encode(text)`). `MessageBuffer.asNative` extracts a header block with `Buffer.from(chunk, 0, length)`, and for a typed array `Buffer.from` ignores the offset and length arguments — so the reader takes the whole chunk as one header block and rejects the message with "Message header must separate key and value using ':'". **NEEDS A RULING — a server command's exit code is taken verbatim on purpose, and R-S5-12 says the opposite.** `settleVerbatimExitCode` records what the handler returned and the engine's own 130/143 mapping is skipped, deliberately: `runExitCode`'s comment names "a server command's protocol conclusion" as one of the two codes that "were never this CLI's to state". R-S5-12 says signals are engine-owned, which holds for every other command kind. Both texts cannot be right. `lsp` currently sides with R-S5-12 and translates the signal itself — 143 for SIGTERM, 130 otherwise, whenever `io.signal` fired — and `test/orm/lsp.test.ts` pins both branches, which nothing did when this was first written. The cost of that choice is visible today: a SIGTERM arriving after a clean `shutdown` reports 143 for a conversation that concluded correctly at 0, because the handler cannot tell the two apart from `io.signal.aborted` alone. The engine's reading is the stronger one for a server command specifically — the protocol says how the run ended — but adopting it means R-S5-12 stops applying uniformly, and whichever answer wins is inherited by every server command after this one. Owner: the engine's owners together with whoever owns R-S5-12. One ruling, not two texts.

**BLOCKS THE EDITOR EXTENSION — `vscode-languageclient` appends `--clientProcessId=<pid>`, and neither shell accepts it.** Its `NodeModule` server form pushes that argument after the transport flag for every server it spawns, so a VS Code extension built the standard way launches `prisma-next lsp --stdio --clientProcessId=1234`. Declaring the flag is not the fix on its own, and this is the part worth remembering: `vscode-languageserver/node` scans `process.argv` for that argument **when the module is imported**, and installs a three-second `setInterval` to watch the parent — a handle nothing here can reach. **STOP-5's fallback to the target id was too weak, and the token rule now falls through four steps instead of one.** The ruling says "the database name parsed from the resolved connection URL, falling back to the target id when the URL carries none". The target id is a target *kind* — the literal string `postgres`, `mongo` or `sqlite` — so for every connection whose URL has no path segment the token collapsed to a constant, and `--confirm postgres` would have granted data loss in any project, in any environment, forever. The shapes that hit it are ordinary: `postgres://localhost:5432`, `mongodb+srv://cluster/?retryWrites=true`, `prisma+postgres://accelerate.prisma-data.net/?api_key=…`, and a driver connection *object*, which carries `{ database: 'appdb' }` and was being ignored entirely. The rule now reads: the `database` a connection object names; else the database a URL names; else the host that URL points at (`localhost:5432`), which at least identifies *which* server; else the target id. Two parser defects went with it — the path segment was never `decodeURIComponent`d (a database named `my db` produced the un-typeable `my%20db`), and it took the *last* segment where `postgres://`, `mysql://` and `mongodb://` put the database *first* (`postgres://host/db/extra` yielded `extra`). A URL with no host is a file path, so its last segment is still the name. This extends STOP-5 rather than contradicting it; the ruling's fallback survives as the last step. Residual: a libpq `host=… dbname=appdb` keyword string is neither a URL nor an object and still falls back to the target id. Owner: an operator who wants keyword strings parsed.

**`--confirm` is read only when the run is already non-interactive, which reads backwards to everyone who meets it.** The engine consults `--confirm` in the `state.yes || !state.interactive` branch of `prompt.consent` and nowhere else. A deploy script that runs `db update --confirm appdb` from a terminal — the incantation the command's own help used to advertise — does not apply anything: it stops at the prompt and waits for someone to type the name. The working form is `--no-interactive --confirm appdb` (or `--yes --confirm appdb`). "The non-interactive flag only works when the run is non-interactive" is a footgun for every consent command that follows, and it is not visible from the flag's name or from the `CLI.CONSENT_REQUIRED` remediation, which names `--confirm <token>` alone. Owner: prisma-cli, if `--confirm` should imply non-interactivity for the consent it answers; the ORM CLI has corrected its own help and the error-reference entry in the meantime.

**Consent authorises a plan, and nothing binds it to the plan that gets applied.** `db update` connects once and calls `dbUpdate` twice: the first call refuses with the destructive operations, and the second carries a blanket `acceptDataLoss: true`. That second call re-reads markers and re-introspects, so it computes a *fresh* plan — the user consented to plan #1 and plan #2 executes. The window is human-scale (someone reading a list of drops and typing a database name), and closing it properly means a control-API change: `acceptDataLoss` would have to become the set of operation ids the caller consented to, and the applier would have to refuse anything outside it. That is a bigger decision than this round, so the command does the post-hoc half — it keeps the consented ids and reports a `warn` event naming any destructive operation the apply performed that the consent did not cover. The operator finds out; nothing stops it. Owner: whoever owns the control API's destructive-change contract.

**A consent that declares a token can never resolve to `false`, and one that declares an empty token accepts anything.** `prompt.consent` with a token either returns `true` or throws — interactively `confirmByTyping` throws `CLI.PROMPT_INVALID` on a wrong answer, and non-interactively it throws `CLI.CONSENT_REQUIRED` unless a matching `--confirm` is consumed. So `await ctx.prompt.consent(...)` with the result discarded is safe today by an engine invariant expressed nowhere in the calling file — in the one command that drops tables. `db update` now assigns it and refuses on `!granted`. The other half is worse: the token is validated only as "is a string", so `''` passes, and against an empty token `typed.trim() !== token` is satisfied by a bare Enter, while `--confirm ""` grants non-interactively. The command hard-fails with `CLI.CONSENT_TOKEN_UNRESOLVED` when its resolved token is empty or whitespace, but the engine should not accept one either. Owner: prisma-cli, for the empty-token check.

**A scripted answer never renders the prompt, so a test that means to observe the question has to drive stdin.** `createTestCli().run(argv, { answers })` short-circuits inside `ask`: the scripted value is returned before `runtime.stderr.write(rendered)`, and `useClack()` is false whenever `answers` is set. A test that asserts on `run.stderr` after passing `answers` is therefore asserting on the command's *output*, not on its prompt — which is how `db update`'s "names the database and every destructive operation in the question" case came to assert two strings that appear in a successful apply regardless of whether anything was asked. Passing `stdin: 'appdb\n'` instead exercises the line renderer and puts the real question on stderr. Owner: nobody; recorded so the next prompt test does not repeat it.

**A send on a connection the client already left kills the process, and the guard had to be structural.** `vscode-jsonrpc` marks the connection Closed the moment the input stream ends, and every send after that throws synchronously. If that throw escapes a notification handler, jsonrpc catches it and reports it through its logger — which is the connection's own remote console, so the report is another send: it throws again inside a `.catch()`, and the unhandled rejection ends the process. Reproduced against the built binary and in isolation; the CLI test's own exchange reaches it, because `initialized` is dispatched after end of input and the handler warns a client with no dynamic file-watcher registration. The first version of the language-server change guarded four call sites by hand, which is one forgotten send away from re-arming it. `guarded-connection.ts` now wraps the connection once — reads walk its features and hand back guarded functions — so a send added later is guarded by construction, and only the connection's departure is swallowed: any other synchronous failure still reaches the caller. Worth remembering as a class: a library that reports errors over the same channel that failed turns one throw into a fatal one. Owner: closed here.

**Draining on "a turn of the event loop where nothing moved" cannot see a handler that awaits.** The first version bumped a counter on decode, dispatch, write-called and write-settled, and settled when a turn passed with the counter still. Nothing moves while a handler is awaiting, so the window between "dispatched" and "reply written" was invisible; it held together only because `onInitialize` awaits nothing. Measured: script `initialize`, `textDocument/foldingRange`, `shutdown` and `exit` in one chunk — the folding-range handler resolves the document's project, which reads the filesystem — and the old drain answered ids 1 and 3 and dropped 2 on the floor. The reply was not late, it was lost. The count is now explicit: messages the connection is handling (a dispatch covers everything its handler awaits and the write of its reply) plus replies being written, with a separate count of messages decoded but not yet started. Zero on both settles the run. The second count is not perfectly paired — a cancellation the connection answers itself never reaches the dispatcher — so it is written off after 50ms in which nothing at all happened, and any activity restarts that clock. The failure mode is a late exit, never a truncated reply. Owner: closed here.

**A malformed `Content-Length` wedged the server with no way out.** The reader fires an error and returns, leaving the stream desynchronised for good: nothing further decodes, the connection never closes, and the run never settles. Nothing listened for that error, so the process sat alive and unresponsive holding a parser and a config watcher — inherited verbatim from the commander path, where it is equally true. The `Promise<number>` contract is the natural place to fix it: a fatal reader error now writes one line to the host's stderr and settles the run at 1. Measured against the built binary with stdin held open: `Content-Length: not-a-number` exits 1 in milliseconds where it used to hang until killed. Owner: closed here.

**Back-pressure cannot survive the engine's `OutputStream` shape.** `OutputStream.write(text): void` returns nothing to wait on, so the language server's `Writable` adapter has to call its flush callback unconditionally: every write reports flushed the moment the sink has taken it. Before the port the callback propagated to the descriptor, so a client that stopped reading slowed the server down; now it grows the host's own output queue instead, and the diagnostics for a large schema are not small. No handler can do better — the fix is a sink that reports when it drained, which is an engine change. Owner: prisma-cli. Recorded as a divergence too, since it is a behaviour change for every consumer of a server command, not just this one.

**Over half of what `lint:framework-vocabulary` counted was documentation explaining family-blind code correctly.** 427 of the 795 counted lines are comments and JSDoc, and sampling them shows what they are: `* SQL family uses this to impose a deterministic order on indexes`, `* family-parameterized (SQL, Mongo, etc. specialize via TStorage)`, `* Family storage types (SqlStorage, MongoStorage, etc.) extend this`. Those describe genuinely generic mechanisms by naming the families that specialise them, which is the right way to document a generic — so the check was taxing good prose and burying its own signal. The remaining 368 non-comment sites are the real thing: `readonly table: string`, `parentColumns`, `ColumnDefault`, `isColumnDefault`, and error text naming `@prisma/orm-postgres/config`. The check is being replaced by a Biome GritQL plugin plus a counting ratchet, matching the `no-bare-cast` pattern the repo already uses. Syntax-node matching ignores comment trivia for free, which is the behaviour we want rather than a limitation, and Biome supplies per-plugin suppression (`// biome-ignore lint/plugin/no-family-vocabulary: reason`) with a mandatory reason and dead-suppression detection, neither of which a bespoke marker gives. Verified on 2.5.6 before committing to it: identifiers match via `js"$name"` plus an anchored regex, string literals need the `JsStringLiteralExpression()` node kind, and the regex engine has no lookarounds, so token boundaries have to be expressed by consuming characters. Owner: closed here.

**A test asserted an exit code that depended on a real contract emit in a project where the installer was stubbed.** `init-scaffold.test.ts`'s "leaves @types/node alone when the project already pins it" is the only case in its file that omits `--skip-install`, so it is the only one that reaches `emitScaffoldedContract`. The `PackageManagerRunner` handed to `createTestCli` records the add request and returns success without installing anything, and the project directory is an `mkdtemp` outside the repo — so the emit loads a config importing `@prisma/orm-postgres/config` from a tree where nothing was installed. It passes locally and failed in CI, which is the signature of resolution succeeding from `process.cwd()` rather than from the config's own directory. The test's actual subject is which dependencies `init` asks for; the exit code is a precondition it cannot guarantee. It now asserts the envelope before the code, so the next failure prints the finding and its cause instead of only that 0 was not 5 — the reason had been going to `run.json`, never to stdout. The design fix is to make the emit injectable, which is the same refactor that removes the module mock from `init-install.test.ts`. Owner: the injection work.

**The CLI suite is order-dependent at the base commit, and a cold cache is enough to expose it.** Four tests in `test/control-api/client.test.ts` failed on a first full-suite run in two separate worktrees and passed on re-run with the same code, and passed with unrelated edits stashed. The package runs `isolate: false` with `fileParallelism: false` and keeps module-level state — `src/utils/emit-queue.ts` holds a queue — so file ordering decides results. This is the same root cause as the module-mock leakage that produced a green suite testing nothing four separate times: shared module state across files in one worker. Not introduced by the port, and it will keep producing failures that look like flakes until the mocks are gone and the module state is owned by something a test constructs. Owner: the injection work.
